# Re-point: this branch was rewritten on 2026-09-18

Read this once if your checkout of `transfer/rig-rounds` predates 2026-09-18, or if a transfer commit SHA you hold no longer resolves. Everything operational it implies is already in `README.md` and `TESTING-TEMPLATE.md` §7; this file exists to explain what happened and to carry the commands.

## Re-pointing a stale checkout

The branch was re-rooted and force-pushed, so its history is unrelated to whatever you hold and `git pull` will fail on it.

```bash
git fetch fork transfer/rig-rounds
git reset --hard fork/transfer/rig-rounds
```

If you keep it as its own clone rather than a worktree, taking it again is cheaper. It is 9.9 MB and clones in about two seconds:

```bash
git clone --single-branch --branch transfer/rig-rounds https://github.com/o-jcardenass/open-headunit.git ohu-transfer
```

The tip after the rewrite is `fb6823ef`: 14 commits, 362 files.

## What survived, and what did not

Every brief and results file survives **byte-identical**, all 360 of them, verified by sha against the pre-rewrite tip. `README.md`, `TESTING-TEMPLATE.md`, `archive/` and `tools/` are unchanged too.

What did not: **transfer SHAs from before 2026-09-18 no longer resolve.** The files they pointed at are still here under the same paths, so cite files by path. That was already the rule on this branch, for the same reason after the 2026-09-03 re-root.

## Why

The branch is append only, so nothing under `evidence/` had ever been deleted or modified in 167 commits and every capture ever pushed was still alive at the tip: 1170 files, 481 MB of tree, 360 MB of packed objects. That is what made clones and `git gc` slow.

The split was lopsided. The markdown, which is the part anyone reads, was 358 files and 6.0 MB, about 1.2% of the weight. So the cut was made by kind rather than by date: every brief and results file stays however old, and the captures leave.

Truncating history instead would have freed 1.9 MB against the 355.8 MB that dropping the captures freed. Worth knowing if this is ever proposed again.

## Where the captures went

All 810 are archived, not deleted: zipped one per round on the fork release `rig-evidence-legacy`, and indexed by `archive/evidence-manifest-20260918.tsv` here, which gives every file its original path, size, sha256, the zip holding it and the commit that added it.

The fork is public, so no token is needed:

```bash
curl -sL -O https://github.com/o-jcardenass/open-headunit/releases/download/rig-evidence-legacy/evidence-<round>.zip
```

or, where `gh` is authenticated:

```bash
gh release download rig-evidence-legacy --repo o-jcardenass/open-headunit -p 'evidence-<round>.zip'
```

An `evidence/<round>/...` path quoted in any results file written before 2026-09-18 resolves through that manifest.

## What changes in how a round is reported

`TESTING-TEMPLATE.md` §7 is the authority; this is the summary.

Captures do not go in a commit any more. Zip them, upload them as one release asset named `rig-evidence-<topic>-round<N>`, and cite the asset plus a sha256 in the results file instead of a path.

The consequence worth internalising: **anything a verdict rests on belongs in the results file itself**, quoted as a log line with its timestamp. The file has to stand on its own, and the asset is only for re-examining something later.

`.claude/hooks/commit-guard.py` refuses any staged file over 256 KB, or carrying a capture extension, on any `transfer/` branch. An old-habit `git add` stops with an explanation rather than silently re-inflating the branch. Other branches are untouched, and the commit message rules it already enforced are unchanged.

If your own `CLAUDE.md` or round scripts say to write captures into `evidence/<round>/`, or to `git add evidence`, fix that line: it will be refused at commit time.

## Result

1170 files and 481 MB became 362 files and 6.3 MB. The repo's `.git` went from 470 MB to 43 MB, and a single-branch clone from several minutes to 9.9 MB in about two seconds.
